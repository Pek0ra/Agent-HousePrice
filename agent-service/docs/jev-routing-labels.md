# Jev 路由评测标签口径（2026-10-14）

评测集：`tests/data/jev_routing_160.jsonl`，由
`python -m app.evaluation.build_jev_routing_gold` 生成。共 160 条互不重复的中文问题；
八类意图各 20 条，调试集和保留测试集各 80 条，每类各 10 条。
两组不放入同一个问题的直接改写。全部使用 `hive_available=true`、无上文，
因此此集**不衡量** Hive 关闭、跨轮指代、复合任务或生成式复核的表现。

## 数据能力与数据源标签

| 数据源 | 当前 Agent 白名单视图 | 适用问题 |
| --- | --- | --- |
| MySQL | `v_agent_house_listing` | 当前挂牌售房/出租房明细；也可在该视图求均值、数量等 |
| MySQL | `v_agent_district_summary` | 按城市、区县、挂牌类型统计、比较、排名 |
| MySQL | `v_agent_monthly_price_trend` | 按挂牌自然月的数量、平均总价、平均单价、平均月租趋势 |
| Hive | `v_agent_house_info_analysis` | **当前已激活的导入数据集**中的离线明细、统计、比较、排名和按 `listing_month` 的趋势；可用 `dataset_id`、`source_import_task_id` 等字段 |
| Hive | `v_agent_house_data_quality_summary` | 当前已激活导入数据集的有效行数、缺失位置、无效价格/面积、重复源记录、质量分等 |

标注 `source` 时，先确定用户要求的**数据集口径**，再看计算方式：

1. 普通“挂牌房源/房价/租金”问数标 `mysql`。均值、计数、极值、区县排名或比较，
   以及多个挂牌月份的趋势都不自动变成 Hive。`上海房价均值` 因此标 `mysql`；
   “房价”究竟是总价还是单价是后续指标澄清问题，不改变数据源标签。
2. 明确指定 Hive、CSV/离线导入、当前已激活的导入数据集、
   `dataset_id`、`source_import_task_id`、`source_record_id` 的导入记录，标 `hive`。
   仅说“历史”不足以区分：MySQL 的挂牌月视图也能回答其已有月份的趋势。
3. 导入质量、缺失/异常、有效记录或质量分等质量汇总，标 `hive`。
4. 不支持的数据或动作（实际成交、预测、政策、写入等）和无上文时无法理解的省略提问，
   标 `none`。`none` 是最终不查询任何数据源，不代表指定 MySQL 或 Hive 的数据不存在。
5. 数据源选择与可用性分开：用户明确要求 Hive 数据集而 Hive 未启用时应澄清/告知不可用，
   不能悄悄查询 MySQL。仅在证明同一数据集与同一指标口径等价时才允许回退。

## 意图标签优先级

1. `unsupported`：请求范围外数据或不可执行动作；当前系统也可能在 Jev 前将危险写操作拦为 `unsafe_request`。
2. `clarify`：在**无上文**的本评测中缺少关键指代或比较对象，无法明确任务。
3. `data_quality`：问题明确查询导入质量视图的质量、有效性和汇总。
4. `trend`：要求多个自然月的序列、逐月变化或走势；即使指标为月度数量/均价也归此类。
5. `comparison`：对两个或更多明确地区/群体进行对照。
6. `ranking`：要求跨地区/群体排序、前 N 名或最高/最低的地区。
7. `listing_search`：要求逐条房源记录或其字段。
8. `aggregation`：单范围的数量、均值、最大/最小值等标量汇总。

一个问题可能含多个词面特征，以上按**主任务**选择唯一意图。例如“哪个区租金最低”是
`ranking`，“某区最低月租是多少”是 `aggregation`；“按月平均价”是 `trend`。

## 评测与变更规则

- `dev` 可用于分析错误、调整提示词与阈值；`test` 在方案冻结前不运行、不据此修改。
- 每次记录 Jev 原始意图/数据源、概率与置信度、是否触发复核、未经复核的策略结果和耗时。
- 原始 Jev 准确率、未经复核的策略结果、完整生产链路结果是三个不同指标，不能混报。
- 现有评测脚本只调用 Jev；不会调用生成式复核或 MySQL/Hive。
- 该评测集是假定业务标签，不能证明对应城市、日期在实时数据库中一定有记录。

## 调试集初步诊断

下表是改造前的 80 条 `dev` 问题。基线使用旧分类描述；候选描述的口径现已并入
`app/agents/jev_router.py` 的数据集需求判断。
原始响应分别保存在 `docs/evaluation/jev-routing-dev-baseline.json` 与
`docs/evaluation/jev-routing-dev-strict-source.json`。两次调用不是固定种子的配对试验，
因此数字是方向性证据，不应当作为总体准确率承诺。

| 指标 | 当前描述 | 候选描述 |
| --- | ---: | ---: |
| 原始意图正确 | 72/80 | 72/80 |
| 原始数据源正确 | 66/80 | 79/80 |
| 未运行复核时的策略数据源正确 | 63/80 | 76/80 |
| 触发生成式复核条件 | 56/80 | 22/80 |

当前描述的 14 个数据源错误为 `mysql→hive` 12 条、`none→hive` 2 条；
候选描述只剩 `none→mysql` 1 条，且触发低置信度复核。
“上海房价均值”的当前描述重复调用 5 次有 4 次选 Hive，均为低置信度；
候选描述重复 5 次均选 MySQL，获选概率约 0.94–0.95。
这表明源头主要是数据源描述没有清楚说明“普通挂牌统计默认 MySQL”，
而不是该句的意图分类（各次都是 `aggregation`）。

另外，候选描述下仍有 `multiple_tasks`/`depends_on_previous` 假阳性。
例如“给我看上海徐汇区的租房小区和月租”被误当两个独立任务，
“当前激活的导入任务里缺少城市或区县的记录有多少”被误当依赖上一轮。
这解释了原始数据源 79/80、未经复核策略数据源仅 76/80 的差距。
这两份旧报告均未测完整生成式复核或数据库执行。

## 改造后的 160 条路由回归

生产路由现将数据集需求 `scope` 与实际数据源分开：普通挂牌走 MySQL，
明确导入数据或导入质量走 Hive；Hive 不可用时不回退到另一数据集。
独立的 `explicit_import` 判断拦截“明确要求 Hive，却被 scope 判为普通挂牌”的冲突。
布尔判断说明已收短，正向的依赖上文/多任务建议进入结构化复核。

| 阶段 | 调试集 80 | 测试集 80 | 总计 160 |
| --- | ---: | ---: | ---: |
| Jev 原始意图正确 | 79 | 78 | 157 |
| Jev 原始数据源正确 | 80 | 73 | 153 |
| 触发结构化复核 | 20 | 32 | 52 |
| 结构化复核及策略后的数据源正确 | 80 | 80 | 160 |
| 结构化复核及策略后的意图+数据源均正确 | 79 | 80 | 159 |

最终唯一的联合路由错误是 `trend-07`：月度平均单价被 Jev 判为普通聚合，
未触发复核，但仍选对 MySQL。52 次结构化复核无调用失败。
首轮冻结方案的完整 160 条报告为 `docs/evaluation/jev-routing-final-dev.json` 和
`docs/evaluation/jev-routing-final-test.json`；检查测试集错误后新增显式导入口径保护，
回归结果为 `docs/evaluation/jev-routing-guard-dev.json`、
`docs/evaluation/jev-routing-guard-test.json`，最终复核结果为
`docs/evaluation/jev-routing-final-reviewed.json`。

测试集在增加显式导入口径保护前已被查看，后一次回归不再是独立的盲测。
这些指标只衡量此题集上的路由，不能推出真实用户问题的准确率，
也不衡量槽位提取、SQL 生成、数据库可用性或最终答案正确性。
